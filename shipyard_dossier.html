§1

What a harness is, from scratch

Before Shipyard existed there was a linear script: call a model, get code back, hope. A harness is what you build once "hope" stops being an acceptable step in the loop.

An LLM is a single, stateless function call: text in, text out, no memory of whether it was right last time. A harness wraps that call with everything a single call can't provide on its own — and Shipyard's design settled on nine specific things a harness owes the work running through it:

Typed I/O

Every role's output is validated against a Pydantic schema the instant it comes back. Malformed output fails loudly at the boundary, not three steps later as a confusing downstream crash.

Explicit topology

The pipeline's shape is data (graph.py), not a tangle of if/else in the orchestrator. You can read the whole system's control flow without reading its code.

Deterministic gates

A gate is re-evaluated fresh every time it's reached — never cached, never trusted from a prior run — because the one thing worse than a slow gate is a gate that lies.

Bounded retries

A failure gets a specific, capped number of chances to resolve, then surfaces to a human — it never loops silently until someone notices the bill.

Safe workspace isolation

Every file write is checked against the project root before it touches disk. No role's output — however confidently wrong — can escape its sandbox.

Durable evidence

State and an append-only trace are both written to disk continuously, not assembled at the end from memory that a crash can erase.

Resume, not restart

An interrupted run picks up exactly where it stopped. Retrying a failure and resuming a crash turned out to be the same mechanism once framed correctly (§3).

A reviewable artifact

The output isn't just files — it's files plus a trace that proves how they came to exist, so a human reviewer inherits evidence, not a black box.

The ninth thing — the one that took the longest to earn — is knowing which of these guarantees a human still has to provide. Shipyard's biggest single architecture change (§4, §6) was discovering that "did this contract overshoot what was actually asked for?" is a judgment an LLM checking another LLM's output can't reliably make on its own, and building the harness to hand that one decision to a person instead of automating it away.

§2

Architecture

Every request flows through the same five stages, regardless of which of the eight pipeline nodes triggered it. Two side channels — one durable, one ephemeral — run alongside every stage without either one owning the other.

Every component, and what it actually does

FileRole
graph.pyThe whole pipeline's topology as data — nodes, gates, classifier routes, retry budgets. Nothing here executes anything; it's read by the walker.
engine.pyThe generic walker. Has no idea "plan" means the Planner — it just walks graph.py and calls whatever NODE_HANDLERS says to run. Owns retry/reset logic, the human-gate pause/resume mechanism, and running build/verify concurrently.
schemas.pyEvery role's I/O contract as a Pydantic model — the hard validation boundary where model output re-enters the system.
agents.pyThe seven LLM role functions. Enforces Builder/Verifier independence explicitly (Verifier is never given Build's output).
prompts/*.md + prompts.pyEach role's system prompt as its own file, loaded fresh on every call — editing a prompt takes effect immediately, no redeploy.
llm_client.pyThe only place that talks to a model. Streams every call, classifies provider failures into named states, resolves each role to a capability tier, and enforces a hard request timeout.
redaction.pyThe secrets boundary. Scans every outbound prompt for credential-shaped content before it leaves the process.
runtime.pyIn-process, non-durable bridge: cancellation events, live streaming buffers, and the redaction-notification handoff — reset on restart by design.
sessions.pyThe durable state snapshot and the append-only evidence trace. Thread-safe (a lock protects concurrent event writes from the parallel build/verify group) and crash-safe (atomic file replace).
execution.pySandboxed file writes, the real npm test runner with a working Windows-safe process-tree timeout, and TAP output parsing.
context.pyAssembles what a role sees of the target project — a capped, honestly-labeled file listing, prioritized by the contract's own named files.
memory.pyAGENTS.md's two tiers: permanent, hand-edited domain rules, and a rolling, recurrence-tracked log of patterns the Calibrator extracts.
factory.pyThe HTTP surface. Every mutating endpoint returns immediately; the actual walk runs on a background thread.
dashboard.htmlThe live view: the graph itself, per-node status, live-streaming output, the human plan-review panel, and a warning when a budget looks stuck.
tools/check_github_token.pyA standalone pre-flight check for a new external integration's credentials — built after paying for the lack of one twice (§4).

Every arrow into plan, build, or verify also resets that node's cached output — the same reset that makes a bounded retry work is what makes resuming a crashed run work too: a resume is just a walk with nothing reset, so an already-succeeded node skips itself. There is no separate "resume mechanism"; there's one walker and two ways to arrive at its starting node.

§4

Problems found, in the order they were found

Every one of these surfaced by actually running the system — none were caught by code review. That's the throughline: this harness's real test suite was live operation, and the automated tests came after, as regression coverage for what running it for real had already taught.

1
No route existed for "the test is broken, not the code"
foundfixed

An Arbiter correctly diagnosed a broken test fixture in its own explanation text — but had no classification label better than "bug" to pick, so it sent the fix to the Builder, who never sees test code and could never touch it. A real retry burned for nothing.

Fix: added test_gap to both classifiers, mirrored on the reactive (Reviewer-side) and proactive (test-gate-side) paths, sharing one budget.
2
An 8-point spec became 21 invented constraints
foundfixed

The Planner turned a short, real feature request into 21 constraints and 20 acceptance criteria — inventing cross-host lock races and distributed-coordination requirements nobody asked for.

Fix, round one: an explicit traceability rule in PLANNER_SYSTEM. Fix, round two (below): a human gate, because the rule alone wasn't enough.
3
Build and Verify silently diverged on an interface
foundfixed

Builder and Verifier never see each other's code by design — but a real run had them independently invent different shapes for the same operation (review(id, {decision, approver, reason}) vs. approve(id, approver, reason)), because the contract never pinned the exact signature down.

Fix: "EXACT INTERFACES ARE MANDATORY WHEREVER THEY MATTER" — the Planner must specify literal function signatures whenever both sides need to converge on one.
4
Windows subprocess handling: npm resolution, encoding, and a 60-second timeout that hung for 89 minutes
foundfixed

subprocess.run(["npm",...]) can't resolve npm.cmd without a shell; text=True silently used the OS codepage and crashed on real UTF-8 output. Worse: on Windows, npm test spawns node.exe as a grandchild that survives a timeout's kill signal and keeps stdout/stderr pipes open — a "60-second timeout" once hung for 89 minutes before it was found.

Fix: shutil.which() resolution, explicit UTF-8 decoding, and a real process-tree kill (taskkill /T /F) with a polling wait loop instead of a single blocking communicate(timeout=).
5
The Verifier's own retries accumulated instead of converging
foundfixed

The Builder gets shown the real, current state of the project before every retry; the Verifier didn't — so a retry invented a new test filename instead of fixing the old one. Four abandoned generations of a test suite, each spinning up its own mock server, ended up running simultaneously under Node's default test discovery. A "60-second" test run genuinely could not finish even at 180 seconds.

Fix: gave verify the same current-file visibility build already had, and made test/ writes fully replace the directory instead of adding to it — a retry's response is now the complete, authoritative state of its own test suite.
6
No request timeout — a call once hung 13+ minutes with no ceiling in sight
foundfixed

The SDK's own default timeout (roughly 10 minutes, times its own retries) meant a genuinely hung network call could stall the whole harness for over 20 minutes before anyone could be sure it wasn't just slow.

Fix: an explicit 300-second request ceiling, chosen with real headroom above every observed real call's duration.
7
A run that was "cancelled" kept running
foundfixed

The harness had no real cancel mechanism — closing a client didn't stop server-side execution. A mistakenly-submitted run kept executing after being believed stopped, and overwrote a proven, live-verified test suite. It was recovered from durable session state, but it was close.

Fix: cooperative cancellation (runtime.py) checked at the walker's node boundary, inside the LLM streaming loop chunk-by-chunk, and inside the test runner's wait loop — proven live in two later runs, once mid-streaming-call.
8
No secrets boundary, and no way to tell a quota problem from a bad implementation
foundfixed

Two structural gaps found in the same review: every role sent full file contents and the raw feature request to the model with zero scanning, and every inference-layer failure — a real rate limit, a blocked model, a genuine bug — surfaced as the same generic error string.

Fix: redaction.py scrubs credential-shaped content before every call (proven live — a real API call echoed back only the redaction placeholder, never the planted secret). llm_client.InferenceError and its subclasses (ModelBlocked / AllowanceExhausted / CapacityInsufficient) now classify provider failures from the real SDK exception types.
9
The test suite had been quietly polluting the real, shared memory file
foundfixed

Adding recurrence-tracking to the Calibrator's rolling patterns revealed something the old, duller dedup logic had been masking: the test suite had been writing to the real AGENTS.md the whole time. One pattern showed seen=22 — 22 silent writes from test runs, invisible until a better counter made the number visible.

Fix: isolated memory.MEMORY_PATH in the autouse test fixture, and cleaned the real file back to its legitimate history.
10
A live, unscripted Builder wrote its own test file
foundfixed

The Builder is told it never sees test code — but nothing stopped it from writing one. A real run had it return a self-authored test alongside its implementation. It happened to be overwritten by the Verifier's own file through a filename coincidence — a Builder grading its own work was one different filename away from actually happening.

Fix: _handle_build now structurally strips any test/-path file from a Builder's output — from disk and from the persisted record — before Arbiter/Reviewer ever see it.
11
A GitHub token mistake cost two debugging rounds it didn't need to
foundfixed

Fine-grained GitHub PATs don't have a separate "Releases" permission — it's bundled under "Contents," which wasn't known going in. Then a token thought to be correctly scoped turned out to still be read-only, only discovered when a real publish call failed.

Fix: tools/check_github_token.py — a standalone pre-flight check for exactly this, run before any integration code gets written against a new credential.
§5

Optimizations & improvements

Every number below is measured from a real run's own event timestamps, not estimated.

Concurrent build and verify

build and verify never depended on each other's output — the Verifier is deliberately never given the Builder's code. Running them on separate threads instead of in sequence was proven twice, live:

Run 1
~38% faster
started 4ms apart
Run 2
~19% faster
started 3.6ms apart

Per-role model tiers

All seven roles shared one model regardless of task weight. Roles now route to one of three capability/cost tiers based on what the task actually needs:

TierRolesWhy
Flagshipplanner, builder, verifier, reviewerCascading, hard-to-undo judgment — a bad contract or verdict ripples through the whole run.
Midarbiter, review_arbiterA bounded, enum-shaped classification with real stakes but a narrower task than open-ended architecture.
LightweightcalibratorExtracting a handful of short strings from a summary — the lowest-stakes call in the harness.

Streaming, live output, and honest truncation

Every call now streams — both to power the dashboard's live per-node output and to make cancellation responsive mid-call, not just between nodes. Separately, the two places context used to truncate silently (a 200-file project listing, a 150KB file-content cap) now say so explicitly in the prompt, and prioritize the contract's own named files ahead of whatever a directory walk happens to find first.

Cost visibility and a stuck-run signal

Tokens were tracked per node but never summed — a per-run rollup now exists everywhere a session is inspected. A new detector flags when the same retry budget exhausts more than once across a session's history — checked against real history, it immediately flagged the one session that actually deserved it (three separate budgets, one exhausting eight times) and stayed quiet on a session that needed a couple of legitimate grants and converged fine.

Smaller, cheaper cleanups

  • A redundant second test-suite run (extracting structured failure detail) now checks package.json's test script first, and skips itself entirely for a project that isn't using Node's built-in runner.
  • Prompts moved from hardcoded strings in agents.py into their own files, loaded fresh on every call — editing wording no longer needs a code change.
  • Session.save() writes atomically (temp file, then replace) after a real JSONDecodeError from a reader catching a mid-write file, made more likely once background threads and concurrent nodes existed.
§6

What we learned

Three ideas kept recurring, from the first linear script to the current graph.

A harness's real test suite is running it for real

Every problem in §4 was found by operating the system against a real target and a real model — none by reading the code. Unit tests came after, as regression coverage for what live operation had already taught. That ordering isn't a shortcut around testing; it's the honest acknowledgment that an LLM's actual behavior — what it chooses to write, how two independent roles happen to diverge, what a model does under real network conditions — isn't something a scripted fake can predict in advance.

Structural enforcement beats a prompt instruction, every time it's affordable

"The Builder doesn't see test code" was a true sentence in a prompt for a long time before it was also true of the code — and the gap between those two is exactly where a live run found the Builder writing its own test file (§4.10). The same pattern repeats everywhere it mattered: path-escape prevention isn't a request not to escape the sandbox, it's a resolved-path check; the secrets boundary isn't a request not to leak, it's a scan before every call leaves the process. A rule a role merely reads is a rule it can eventually not follow.

Some judgment calls belong to a person, not a second opinion from the same kind of model

The single largest architecture change in Shipyard's history was replacing an automated "did this contract overshoot the request" check with a human gate. Not because automating it was lazy — a real, carefully-worded LLM check existed and worked much of the time — but because asking one LLM to judge whether another LLM over-elaborated is a narrower guarantee than it sounds like: both are drawing from the same kind of reasoning about what counts as reasonable scope. A human reading the same contract catches drift a same-class check sometimes won't, and costs nothing extra when the contract was already fine — it's held zero false approvals since it started.

A number worth sitting with: the one session that never should have kept running (a contaminated legacy contract, retried past the point of no return) burned 105,154 tokens — the second-highest of any session — before "start fresh" was recognized as the only real fix. The stuck-run detector in §5 exists directly because of that number.

§7

Current status

Where things actually stand, and what's still open.

Proven live

The full graph — human gate, concurrent build/verify, real cancellation — has completed end to end on a real project, twice. A real GitHub repository has gone scan → prepare → approve → publish, with two real prereleases independently verified against the live API. A thin review console wraps the CLI by subprocess only, its full route surface exercised live against the real repo.

Still open

The new topology's classifier/routing paths haven't been forced by a genuine live retry — both real runs so far converged on the first attempt. Redaction has fired in one deliberate live test, never in an organic run. server.js hasn't had the same security read-through release-manager.js has.

Repositories

  • Shipyard — the harness itself, this document's subject.
  • Release Manager — the CLI + review console built through it, in its own repository (kept separate deliberately: the same test-directory-replace mechanism that fixed §4.5 would otherwise risk overwriting the CLI's own proven test suite if both lived in one project).
