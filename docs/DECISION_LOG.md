# Decision Log

Every row below is a real decision made while building Shipyard and Release
Manager, in the order it was made. "Why" is the actual reasoning at the
time — including the times an earlier decision got revisited once real
evidence contradicted it (rows 3, 10, 17 in particular). Dates are drawn
from real commit and session timestamps, not remembered after the fact.

| Date | Decision | Options considered | Why |
|---|---|---|---|
| 2026-09-11 | Phase graph as declarative data, walked by a generic engine | Hardcode each phase transition directly in Python control flow, vs. describe the topology as data (`graph.py`) and have one generic walker (`engine.py`) execute whatever it's given | Node-specific behavior (which agent runs, what it writes) shouldn't require touching the code that walks the graph. A generic walker means gates, retries, and resume are one mechanism regardless of how many nodes the topology grows to. |
| 2026-09-11 | Hand-rolled orchestration loop, not an agent framework | Use an existing agent-framework abstraction (hidden tool-loop/planning internals) vs. author the control loop directly in plain Python | Every decision the harness makes needs to be visible and inspectable — a framework's internal loop is exactly the kind of hidden non-determinism this project exists to avoid. |
| 2026-09-16 – 2026-09-19 | Replace the automated `scope_gate` classifier with a human `plan_review` gate | Keep an LLM (`scope_gate`) judging another LLM's (the Planner's) scope automatically vs. insert a real human checkpoint before any build work starts | Live evidence (session `5601a0c16d7a`, and later `d638d9ab45b3`) showed the automated version looping — the Planner turned an 8-point spec into 21 invented constraints, and the automated scope check disagreed with itself across retries, burning real budget an operator could have resolved in seconds by reading the plan. A human is strictly more trustworthy here than an LLM checking an LLM. |
| 2026-09-19 | Run `build` and `verify` concurrently, not sequentially | Keep them sequential (simpler control flow) vs. run them on separate threads as one `PARALLEL_GROUPS` step | The Verifier is deliberately never given the Builder's output (independence by design), so sequential ordering only ever slows the run for no correctness benefit. Measured live: ~38% and ~19% wall-clock savings across two separate real sessions. |
| 2026-09-19 | Real cooperative cancellation, checked at three boundaries | Rely on the client just disconnecting (no real stop) vs. a checked `threading.Event` at the walker's node boundary, inside the LLM streaming loop, and inside the test-runner's wait loop | A run believed "cancelled" had kept executing server-side and overwritten a proven, already-verified test suite (recovered only because of durable session persistence). A real, checked mechanism was the only fix that couldn't recur by accident. |
| 2026-09-19 – 2026-09-20 | An explicit secrets-redaction boundary at the single LLM call site | Trust that nothing secret-shaped ever reaches a prompt vs. scan and redact at the one chokepoint every role's call passes through (`llm_client.call()`) | A direct check found zero redaction logic anywhere in the pipeline — every role sent full file contents and the raw feature request with no scanning at all. One chokepoint is unbypassable by construction; scattered checks per-role are not. |
| 2026-09-20 | Named inference-failure hierarchy (`ModelBlocked` / `AllowanceExhausted` / `CapacityInsufficient`) | Keep catching `Exception` generically and surfacing one generic error string vs. classify from the real SDK exception types | An operator staring at a stuck run needs to know whether it's a quota problem, a blocked model, or an actual bug — those require completely different responses, and a generic string collapses the distinction. |
| 2026-09-20 | Per-role model tiers (sol / luna / terra) instead of one model for every role | One model for all seven roles vs. tier by each role's actual judgment load, using the real capability/pricing differences between the three available models | Arbiter and ReviewArbiter make genuine judgment calls (is this scope creep, is this test file broken) that warrant the strongest tier; Calibrator's job (summarize a rolling pattern) doesn't need the same capability, so paying for it there is waste. |
| 2026-09-20 | CommonJS pinned as the fixed module convention | Let each run's Builder/Verifier choose ES modules or CommonJS freely vs. pin one explicitly in the role prompts | Checked history across 5 real prior projects before deciding anything: CommonJS had already emerged as a 100%-consistent, unprompted default. Pinning it just codified what was already true rather than fighting or second-guessing an established real pattern. |
| 2026-09-20 | Structural test-path enforcement in `_handle_build` | Rely on the Builder's system prompt saying "you never see test code" vs. strip any `test/`-path file from `BuildOutput` in code, from disk and the persisted record alike | A live, unscripted run (session `5dc049bfb535`) had the Builder actually return a self-authored test file alongside its implementation — it only avoided grading its own work by a filename coincidence with the Verifier's real output. Proof the prompt-only rule wasn't sufficient; only code enforcement is trustworthy. |
| 2026-09-20 | Retry budgets set small and fixed per route, then halved again later | Unbounded retries (risk of infinite loops on a genuinely unfixable contract) vs. small fixed budgets per classifier route, initially `build_retry`/`review_retry` at 4/6, later tightened to 2/2 (2026-09-21) | Even the original, wider budgets turned out to be more headroom than any observed real run actually consumed — real sessions converged well inside 2 retries per route. Tightening them was a direct response to that evidence, not a guess. |
| 2026-09-20 | A generated HTML dossier (`shipyard_dossier.html`) replaces a static `ROADMAP.md` | Keep a bullet-point markdown roadmap vs. build a real retrospective document with measured numbers, an architecture diagram, and the actual incident timeline | By this point the project had enough real, evidenced incident history to tell its own story — a narrative document with real numbers serves that better than a list of future intentions. |
| 2026-09-21 | Release Manager lives in its own separate GitHub repo, not inside Shipyard's `workspace/` | Keep the built product inside Shipyard's (gitignored) `workspace/` vs. give it an independent repo | `workspace/` had already produced one real near-miss (a mistaken run's `verify` step overwrote a live, proven test suite before cancellation existed). A separate repo removes that entire collision class and keeps "evidence Release Manager was built through Shipyard" cleanly separable from "the harness's own internal workspace." |
| 2026-09-21 | Render over Fly.io for hosting the review console | Fly.io (persistent volume, stronger state-persistence guarantee) vs. Render (no persistent disk on the free tier, but no payment method required) | Hit live, mid-setup: Fly requires a card on file even for free-tier-eligible usage. Render needed none. Accepted the weaker state-persistence guarantee (documented as a known limitation) in exchange for not requiring a payment method for a portfolio deployment. |
| 2026-09-21 | Three evidence routes (`/evidence/trace`, `/evidence/session`, `/evidence/events`) are the only routes exempt from Basic Auth | Gate every route uniformly, including evidence, vs. carve out exactly three fixed, allowlisted routes as public | Evidence that a product was really built through Shipyard is only useful to a reviewer if they can see it without asking for your login credentials — auth-gating the proof defeats its own purpose. |
| 2026-09-21 – 2026-09-22 | Hand-write the final restoration of `release-manager-review-ui`'s test suite, instead of another Shipyard grant-and-retry round | Grant `test_retry` budget again for a sixth attempt at an increasingly "clever" (and increasingly fragile) dynamic test-inspection strategy vs. write one consolidated, hardcoded test file by hand | Five consecutive real, distinct defects and ~179K cumulative tokens against one file's test suite was a legitimate cost/time tradeoff to stop paying, not a sign the underlying capability was broken. Explicitly logged as breaking the "everything built through Shipyard" chain for this one file, deliberately. |
| 2026-09-22 | Git worktree isolation: every Shipyard run gets its own linked worktree and branch | Keep every run writing directly into one shared project directory (status quo since project start) vs. give each session an isolated git worktree, merged into the canonical directory only on real completion | The same class of collision risk that had already caused the `workspace/` near-miss above — two runs (or a run and a manual test) touching one project directory at the same time — was still structurally possible. A worktree makes the isolation real, not just a documented practice to remember. |
| 2026-09-22 | Worktrees placed as top-level siblings of every real project, not nested one level deeper | `workspace/.worktrees/<project>__<session>` (the original implementation) vs. `workspace/<project>__<session>` directly under `workspace/` | Found live, before it could waste a run: the nested location silently broke any project's own code that resolves another project as a relative sibling — exactly what `release-manager-review-ui`'s `server.js` does to find its CLI. A worktree has to resolve `..` the same way the canonical directory itself would. |
| 2026-09-22 | `RELEASE_APPROVERS` is a required environment variable (fails closed) | Required, fail-fast if unset (matching `GITHUB_TOKEN`'s existing convention) vs. optional with a fallback that allows any approver when unset | The bug being fixed was exactly "anyone can approve under any claimed identity" — an optional-with-fallback design would silently reintroduce that same gap the moment someone forgot to set the variable. Fail-closed was the only design that actually closes it. |
